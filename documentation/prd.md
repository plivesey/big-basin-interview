# Product Requirements Document: Service Booking Assistant

**Version:** 1.0
**Date:** 2025-12-17
**Status:** Draft
**Owner:** Backend + Core Development

---

## Executive Summary

An AI-powered conversational assistant that enables users to discover local service providers and schedule appointments through natural language interaction. The system uses LLM technology to parse user intent, conduct intelligent searches, and guide users through booking confirmation—all via a chat interface.

**Target Timeline:** 2-3 days
**Core Focus:** Backend extension with stateful workflows, LLM reliability, and calendar integration

---

## Problem Statement

Finding and booking local service appointments (hair salons, auto mechanics, dentists) typically requires:
- Navigating multiple websites or apps
- Understanding complex availability systems
- Manually coordinating schedules

Users need a conversational interface that understands natural requests and handles the entire booking flow end-to-end.

---

## Goals & Success Metrics

### Primary Goals
1. Enable zero-friction service discovery and booking via natural language
2. Demonstrate production-ready LLM integration patterns
3. Implement robust stateful workflows with graceful error handling

### Success Metrics
- Users can complete a booking in a single conversation (<3 minutes)
- LLM successfully extracts intent from ambiguous requests (>90% accuracy)
- System handles edge cases (interruptions, API failures) gracefully
- End-to-end booking flow is traceable via structured logs

---

## User Personas

**Primary Persona: Time-Constrained Professional**
- Needs to quickly book appointments during work breaks
- Prefers conversational input over form-filling
- Expects immediate availability information
- Values confirmation and calendar integration

## User Stories

### Discovery & Search
```
As a user
I want to describe what service I need in natural language
So that I can find providers without navigating complex menus

Acceptance Criteria:
- Assistant parses service type, location, and preferences from free-text input
- System handles clarifying questions when request is ambiguous
- Results display as structured provider cards
```

### Booking Flow
```
As a user
I want to select a provider and view available time slots
So that I can complete my booking in one session

Acceptance Criteria:
- Available slots displayed based on provider's working hours
- Assistant confirms booking details conversationally before finalizing
- Booking persists to database with confirmation message
```

### Workflow Continuity
```
As a user
I want to resume my booking if I get interrupted
So that I don't have to start over

Acceptance Criteria:
- Workflow state persists across sessions
- User can return and continue from last step
- System handles timeout and abandonment gracefully
```

## Functional Requirements

### 1. Conversational Interface

**FR-1.1: Natural Language Input**
- User can type free-form requests
- LLM parses intent into structured data: `{ serviceType, location, timePreference, budget }`
- System maintains conversation context across multiple turns

**FR-1.2: Clarification Handling**
- When request is ambiguous, assistant asks targeted follow-up questions
- Examples: "What type of service?", "Which neighborhood?", "Morning or afternoon?"

**FR-1.3: Response Generation**
- All assistant responses generated by LLM (no canned strings)
- Responses match conversational tone and provide actionable next steps
- Structured data (provider cards, time slots) embedded in responses

**FR-1.4: Message History**
- Display full conversation history within session
- Visual distinction between user and assistant messages

**FR-1.5: Markdown Message Rendering**
- Assistant messages should render markdown formatting correctly
- Supported formatting:
  - Bold text (**text** or __text__)
  - Italic text (*text* or _text_)
  - Ordered lists (1. 2. 3.)
  - Unordered lists (- or *)
  - Line breaks and paragraphs
- Code blocks preserved for technical responses (if present)
- HTML sanitization to prevent XSS attacks

### 2. Provider Search

**FR-2.1: Mock Database**
- 5-10 providers with realistic data:
  - Name, category, location (lat/lng or address)
  - Rating (1-5 stars)
  - Working hours (weekly availability windows)
  - Services offered
- Store in SQLite with read/write capability

**FR-2.2: Search Execution**
- Backend filters providers based on extracted criteria
- Ranking by relevance (category match > proximity > rating)
- Return top 5-10 results

**FR-2.3: Result Display**
- Provider cards with: name, category, rating, distance/location
- Click to view details and available time slots

### 3. Booking Flow

**FR-3.1: Time Slot Selection**
- Display available slots for selected provider
- Slots based on provider's working hours and existing bookings
- Minimum slot duration: 30 minutes

**FR-3.2: Confirmation Dialog**
- Assistant conversationally confirms:
  - Provider name
  - Service type
  - Date and time
  - User contact info (pre-filled for single-user MVP)
- User must explicitly confirm before booking created

**FR-3.3: Booking Persistence**
- Store booking in database with:
  - Unique ID, user ID (static for MVP), provider ID
  - Service type, scheduled time
  - Status: `pending`, `confirmed`, `cancelled`
  - Created timestamp

**FR-3.4: Confirmation Response**
- Display booking confirmation with all details
- Include booking ID for reference
- Show calendar event creation confirmation (if integrated)

### 4. Stateful Workflow Engine (Backend Extension)

**FR-4.1: State Machine**
- Model booking flow as explicit state machine:
  ```
  PROVIDER_SEARCH →
  PROVIDER_SELECTION →
  CONFIRMATION → BOOKING_CREATED → COMPLETE
  ```
- Each state has defined transitions and valid actions

**FR-4.2: Persistence**
- Store workflow state in database: `{ sessionId, currentState, context, lastUpdated }`
- Support resumption: user can close chat and return to same state

**FR-4.3: Interruption Recovery**
- User can navigate backward (change provider, change time)
- System resets to appropriate state without data loss

### 5. LLM Reliability (Backend Extension)

**FR-5.1: Retry Logic**
- Exponential backoff for API failures: 1s, 2s, 4s (max 3 retries)
- Distinguish retryable errors (5xx, timeout) from non-retryable (4xx)

**FR-5.2: Timeout Protection**
- 30-second timeout for LLM API calls
- Fallback to generic error message if exceeded

**FR-5.3: Output Validation**
- Parse and validate LLM structured outputs against schema
- Reject malformed responses and retry with refined prompt
- Sanitize strings before database insertion (SQL injection protection)

**FR-5.4: Idempotency**
- Booking creation is idempotent (duplicate requests don't create duplicate bookings)
- Use idempotency keys based on `sessionId + timeSlot + providerId`

### 6. Calendar Integration (Backend Extension)

**FR-6.1: Google Calendar API Setup**
- Authenticate with Google Calendar API (use service account for MVP)
- Store calendar ID in configuration

**FR-6.2: Conflict Detection**
- Before confirming booking, check user's calendar for overlapping events
- If conflict detected, notify user and suggest alternative times

**FR-6.3: Event Creation**
- On successful booking, create calendar event with:
  - Title: `[Provider Name] - [Service Type]`
  - Time: scheduled slot
  - Description: booking details and provider info
  - Location: provider address
- Store calendar event ID in booking record

**FR-6.4: Error Handling**
- If calendar creation fails, still complete booking but log error
- Provide user with manual calendar details

### 7. Observability (Backend Extension)

**FR-7.1: Structured Logging**
- Log all workflow state transitions: `{ timestamp, sessionId, fromState, toState, context }`
- Log LLM requests/responses: `{ requestId, prompt, response, latency, tokens }`
- Log booking operations: `{ bookingId, providerId, userId, action, result }`

**FR-7.2: Request Tracing**
- Generate unique `requestId` for each API call
- Include `requestId` in all related log entries
- Enable end-to-end trace of single booking flow

**FR-7.3: Error Logging**
- Capture full error context: stack trace, request payload, user session
- Categorize errors: `llm_failure`, `db_error`, `calendar_error`, `validation_error`

## Technical Overview

For detailed technical architecture, implementation patterns, and integration strategies, see the **[Engineering Requirements Document (ERD)](./erd.md)**.

### Tech Stack Summary

**Frontend:** React, TypeScript, Tailwind CSS, Socket.io/SSE client
**Backend:** Node.js, Express, TypeScript, SQLite, Drizzle ORM
**AI Integration:** Claude SDK (Anthropic)
**Calendar:** Google Calendar API
**Real-Time:** WebSockets (Socket.io) or Server-Sent Events

### Key Architectural Decisions

See [ERD Section 4-7](./erd.md#4-claude-sdk-integration-strategy) for detailed analysis and options:

1. **Real-Time Communication:** WebSockets vs SSE (see ERD §5)
2. **UI State Synchronization:** Tool-based commands vs structured responses (see ERD §6)
3. **Progress Updates:** Extended Thinking vs manual events (see ERD §7)
4. **Backend Architecture:** Modular service-based design (see ERD §3)

### High-Level Architecture

```
Client (React)
    ↕ WebSocket/SSE
Express API Server
    ↕ Tool Execution Loop
Claude SDK → Tools:
  - search_providers
  - display_provider_cards
  - check_calendar_conflicts
  - create_booking
    ↕
SQLite DB + Google Calendar API
```

**Note:** All technical specifications, data models, API designs, integration challenges, and solutions are documented in the [ERD](./erd.md)

## Non-Functional Requirements

### Performance
- API response time <2 seconds (excluding LLM latency)
- LLM response time <5 seconds (P95)
- Support 10 concurrent sessions (MVP sufficient)

### Reliability
- LLM API success rate >95% (with retries)
- Database uptime 100% (local SQLite)
- Graceful degradation when calendar API unavailable

### Usability
- Clear error messages for user-facing failures
- Loading states during LLM processing
- Conversation history persists within session

### Maintainability
- TypeScript strict mode enabled
- All functions typed with interfaces
- Unit tests for critical paths (workflow state machine, LLM validation)
- Comprehensive README with setup instructions

### Security
- Input sanitization to prevent SQL injection
- LLM output validation before execution
- No hardcoded API keys (use environment variables)

### Glossary
- **LLM**: Large Language Model (Claude, GPT, Gemini)
- **Intent**: Structured representation of user's goal extracted from natural language
- **Workflow State**: Current position in booking flow state machine
- **Tool Use**: Claude SDK feature allowing AI to call functions/APIs autonomously
- **Idempotency**: Property ensuring duplicate requests produce same result
- **Conflict Detection**: Checking for calendar overlaps before booking
- **Extended Thinking**: Claude SDK feature showing AI reasoning process to users
- **State Machine**: Formal model of workflow transitions with defined states and rules
